# 性能观测与结果局限

## 可选观测

```sh
RUASK_TRACE=1 ruask git status
```

stderr 末尾追加一条 `ruask-trace:` JSON，记录单调时间、请求大小及 HTTP 状态等数值。默认关闭，不记录查询、回答、地址或凭据，不改变 stdout 和退出语义。阶段覆盖配置完成、HTTP 开始/响应/首字节、首正文、完整行/命令候选、结束和退出。

Trace 的命令标记只表示符合格式的完整命令候选，不证明正确性。客户端时间不能独立拆分网络、网关排队、服务缓存和模型推理。测量定义及质量核对见[测试说明](testing.md)。

## 显式推理设置

支持 `thinking.type` 扩展的 OpenAI 兼容服务可设置 `OPENAI_THINKING=enabled|disabled`，或用户文件中的 `[openai].thinking`。环境变量优先，未设置时省略字段，继续采用服务默认值；原生 Anthropic 忽略此设置。不支持扩展的服务可能拒绝请求。

当前 CLI 不提供 `reasoning_effort` 配置，也不自动更改用户配置或模型策略。

## 当前采用的架构（2026-11）

2026-11-09 至 11-10 的架构对比实验（单一 OpenAI 兼容服务，自建 116 题评测集，中英文、Linux/macOS 混合）后，采用以下组合，代码已在 `main`：

- 只有命令名、没有 `-q` 和 stdin，且本地有 tldr 页面时直接渲染页面，不请求模型；
- 其他查询在命令命中页面时，把命令页和同族相关页作为 `reference` 交给模型；
- 精简指令并给出严格的三行格式示例；说明与用途逐字显示，命令整行显示。

实验中的首条正确命令耗时（p50 / p95）：

| 类别 | 纯模型基线（服务默认 thinking） | 采用方案（关闭 thinking） |
| --- | --- | --- |
| 简短命令 | 4.55 s / 6.87 s | 5 ms / 10 ms（本地直出） |
| 子命令 + 问题 | 3.93 s / 14.7 s | 2.36 s / 3.41 s |
| 自然语言 | 2.69 s / 6.29 s | 2.17 s / 3.05 s |
| 管道输入 | 5.63 s / 11.0 s | 2.79 s / 3.33 s |

人工复核后两者均为 116/116 正确，采用方案的格式违规为 0。速度收益主要来自关闭 thinking 和本地直出；`reference` 注入用于在关闭 thinking 后守住冷门工具题的准确率。

局限：

- `thinking` 不是标准参数，CLI 默认仍不发送；上表的“关闭 thinking”需要用户按上文显式设置，且只对支持该扩展的服务有效。
- 只测了一个服务和模型，未测 Anthropic 协议；评测集自建，规则判对的回答只抽样复核，不是独立盲评。
- 向量检索、本地小模型和“先显示 tldr 再补模型回答”均测过但未采用。

## 历史结论（2026-11-04）

此前的单变量研究（Prompt、Thinking、reasoning effort）结论为 INCONCLUSIVE：部分设置测得较低延迟，但当时未同时通过正确性、完整回答质量和安全性验证。上面的架构实验通过 `reference` 注入和格式约束解决了“关闭 thinking 更快但出现质量错误”的矛盾。

本地固定响应回放和客户端微小耗时不能替代真实模型质量、完整回答速度或安全结论；本页不提供跨服务性能保证。
